# Задание 2. Проверочный лист безопасности для бизнес-систем

Проверочный лист информационной безопасности для бизнес-систем компании **PropDevelopment**, составленный по результатам анализа диаграммы контейнеров (C4) и описания системы. За основу взят шаблон проверочного листа ИБ; разделы отобраны и приоритизированы под проблемы и приоритеты компании, добавлен раздел под партнёрские интеграции.

Решение состоит из трёх частей:

1. **Анализ систем** — идентификация систем и их свойств с точки зрения ИБ.
2. **Выбор разделов** проверочного листа с обоснованием.
3. **Заполненный проверочный лист** в формате Markdown-таблицы (ответы проставлены там, где в описании достаточно данных).

## 1. Системы PropDevelopment и их свойства с точки зрения ИБ

| Система | Назначение | Свойства, значимые для ИБ |
|---|---|---|
| **Витрина продаж** (монолит, React) | Подбор и бронирование недвижимости | Внешний доступ через firewall; сбор ПДн (ФИО, телефон, email, расширенная форма); одна из **точек регистрации** клиента |
| **client-mart-app** + client-mart-db | Онлайн-сделка, данные об объектах | Данные сделок (договоры), интеграция с **госорганами (СМЭВ/SOAP)**; юридически значимые данные |
| **client-tour-app** + client-tour-db | Онлайн-тур | Менее чувствительные данные; внешний доступ |
| **client-crm-app** + crm-db (MSSQL) | CRM клиентов | ПДн клиентов; ещё одна **точка регистрации** (карточка/профиль клиента) |
| **client-mart-estate-app** + client-mart-estate-db | Данные о недвижимости | Внутренние данные фонда; интеграция с госорганами |
| **auth-service-1** (Keycloak) + auth-db-1 | Аутентификация клиентов | Учётные/секретные данные клиентов |
| **Витрина сервисов для собственников** (mobile) | Приложение ЖКУ / «Умный дом» | ПДн собственников, платежи, **управление «Умным домом» (замок квартиры)**; внешний доступ; личные устройства пользователей |
| **tenant-core-app** + tenant-core-db | Услуги ЖКУ собственникам | Данные ЖКУ; интеграция с **поставщиками ресурсов ЖКХ и платёжной системой**; **API УК без единых политик** |
| **CRM (ЖКУ)** + crm-tenant-db | Данные о собственниках | ПДн собственников |
| **accountant-service-1** (Keycloak) + auth-db-1 + Active Directory | Бухгалтерский учёт | Финансовые данные; **отдельный контур аутентификации и своя AD** |
| **Active Directory ×2** | Служба каталогов | Учётные записи сотрудников/сервисов; **идентичность фрагментирована** (2× Keycloak + 2× AD) |
| **Хранилище данных** (Greenplum) + **DWH** (S3) | Единое хранилище, BI/отчётность | Агрегирует данные **всех** систем через **CDC**; «**со стороны систем обработки данных нет ограничений на доступ к данным**»; цель — BI/ML/AI |
| **Внешние системы**: Госорганы (СМЭВ), Платёжная система, Поставщики ресурсов ЖКХ (API УК) | Интеграции | Партнёрские API **без единых политик ИБ и системного контроля передаваемых данных** |

**Ключевые наблюдения по безопасности:**

- **Фрагментированная идентичность и несколько точек регистрации.** Аутентификация рассредоточена между 2× Keycloak и 2× Active Directory; клиент регистрируется в нескольких местах без координации → нет единого реестра учётных записей и единого контроля доступа.
- **Нарушена изоляция данных.** Клиент видит чужие данные в личном кабинете; партнёр одной УК имеет доступ к данным другой УК → отсутствуют замкнутые контуры и авторизация на уровне объекта.
- **Неконтролируемые потоки данных.** Единое хранилище наполняется «сырыми данными» всех систем через CDC без ограничений доступа → риск для конфиденциальности и блокировка развития data-продуктов.
- **Небезопасные партнёрские API.** Интеграции с УК без единых политик безопасности, контракты содержат избыточные ПДн.
- **Внешняя экспонированность.** Клиенты и собственники работают через интернет (firewall), мобильное приложение — на личных устройствах.
- **Критичность «Умного дома».** Управление замком квартиры — угроза физической безопасности при компрометации.

## 2. Выбор разделов проверочного листа и обоснование

Сопоставление проблем и приоритетов компании с разделами листа:

| Проблема / приоритет PropDevelopment | Закрывающие разделы |
|---|---|
| **P1.** Нарушен контроль данных (точки регистрации, неконтролируемые потоки, нет ограничений доступа) | I, II |
| **P2.** Небезопасные партнёрские API, нет изоляции арендаторов | **VI**, I, III |
| **N1.** Удовлетворённость клиентов — клиент видит чужие данные в ЛК | I, **VI** |
| **N2.** Развитие BI/ML/AI блокируется управлением потоками данных | II (Data Governance, классификация, анонимизация) |
| **N3.** Реагирование на инциденты и утечки | IV, III |
| **N4.** Соответствие законодательству РФ (152-ФЗ) | II, VI |
| Процесс: специалист по ИБ вне контура изменений | IV (регулярные аудиты, обновление политик) |

**Решение по разделам** (с приоритетом для предстоящего аудита):

| Раздел | Включён | Приоритет | Обоснование |
|---|---|---|---|
| **I. Управление доступом** | Да | **Высокий** | Прямо закрывает корневую проблему P1 (точки регистрации, единый реестр, минимальные привилегии, замкнутые контуры) и жалобы клиентов N1 |
| **II. Безопасность данных** | Да | **Высокий** | Классификация и Data Governance (P1, N2), учёт ПДн и шифрование (N4), резервное копирование и целостность (N3) |
| **III. Защита инфраструктуры** | Да | Средний | Поддерживает изоляцию (сегментация, замкнутые контуры) и контроль гибридного облака; частично закрывает P2 и N3 |
| **IV. Управление инцидентами** | Да | **Высокий** | Реакция на инциденты/утечки (N3) и регулярность аудитов — отвечает на нарушенный процесс вовлечения ИБ |
| **V. Специфические аспекты** | Да | Низкий | Общая ИТ-гигиена (MDM/VPN/физбезопасность). Сохранён для полноты; **MDM неприменим к клиентским мобильным устройствам** собственников (личные устройства) — безопасность мобильного приложения закрывается разделами I и VI |
| **VI. Безопасность интеграций и партнёрских API** | **Добавлен** | **Высокий** | Проблема P2 — топ-приоритет компании, в шаблоне отдельного раздела нет. Закрывает изоляцию арендаторов, единые политики API, минимизацию ПДн в контрактах, авторизацию на уровне объекта (N1, N4) |

> Шаблон проверочного листа допускает адаптацию под контекст компании, поэтому базовые разделы сохранены и отранжированы, а специфичная для PropDevelopment проблема партнёрских интеграций вынесена в отдельный раздел VI.

**Условные обозначения столбца «Да/нет»:** `Да` / `Нет` / `Частично` — где в описании есть основания для вывода; `Нет данных` — где сведений в описании недостаточно (в комментарии указано, что проверить на аудите).

## Итоги

Заполнение листа подтверждает приоритеты предстоящего аудита:

- **Подтверждённые «Нет» сосредоточены в разделах I, II и VI** — это управление доступом, безопасность данных и партнёрские интеграции, что напрямую соответствует двум корневым проблемам компании (нарушенный контроль данных и небезопасные API).
- **Большая доля «Нет данных»** в разделах III–V показывает, что по инфраструктуре, инцидентам и физической безопасности сведений в описании недостаточно — эти области требуют первоочередного сбора информации на аудите.
- Наиболее критичные подтверждённые пробелы: отсутствие изоляции данных (I.9, VI.1, VI.4), единого реестра учётных записей (I.11–I.12), Data Governance и контроля доступа к данным (II.8–II.9), единых политик и контроля партнёрских API (VI.2, VI.6).
